# Actions: named, manual or scheduled jobs per project
Status: direction chosen
Supersedes: —

## Problem
User wants per-project "actions": a named job (console app check/update, git
pull/push, a Claude prompt with values injected from files/params), startable
from the cockpit, with a visible log, and optionally on a schedule (every 5-10
min, nightly). Driving use case: a kanban board where users drop items; an
action syncs the board into git, picks up new items assigned to a person, and
either executes them or investigates them (bug report: data complete?
reproducible on the dev server?) or makes small fixes. Must respect other
running jobs (wait, or skip and catch it next tick). Should be an optional
add-on, not core.

## What exists today (grounding)
- mf-watch is already a scheduler: poll loop 1-15 min, git_sync (pull = inbox,
  push = outbox), dispatches `ready` cmds strictly one at a time.
- The lane already serializes agent work; "is something running?" =
  any cmd with `status: running` (self-update uses exactly this guard).
- Self-update timer (machine-install.md#self-update) is a working example of a
  scheduled action with a guard: systemd timer, one decision per tick, one log
  line, skip while running.
- mf-run: start/stop/status of processes, log per service, cockpit Run card
  shells out to it -> pattern for "button + log tail".
- Cockpit writes only drafts and draft->ready (deliberate: a window, not an actor).
- Decision 0010/0018: "nothing deploy-shaped" in mf-run, widened once.

## Comparison with GitHub Actions / GitLab CI
Same: named jobs in YAML, triggers `workflow_dispatch` (button) + `schedule`
(cron), logs per run, `concurrency:` groups.
Different:
- GH/GL run on an ephemeral clean checkout per run; MagnaFlow works on ONE
  persistent working copy shared with the worker -> concurrency is not a
  nicety but a correctness issue (dirty tree, port locks, rebase conflicts).
- GH/GL are event-driven by the forge (push/PR/issue); MagnaFlow has no server,
  only polling + git (principle VII local-first, forge-neutral).
- GH/GL have DAGs, matrices, secrets, artifacts, marketplace - none needed here.
- Claude Code GitHub Action (issue assigned/@claude -> agent run -> PR) is the
  forge-native version of the kanban use case; works only if the board is the
  forge's issues and you accept PR flow and cloud runners.

## User input (turn 2)
- Wants a hard "busy" rule: while anything runs, nothing else starts; queued
  work just waits.
- Fears "everything via a cmd" is heavy for small questions; numbering past
  9999 is not the real worry.
- Own sketch: `.magnaflow/actions/check-board.md` describing: exit on busy /
  dirty git -> call console app -> exit if nothing new -> pull -> fill cmd
  template -> execute -> push. Results in `.magnaflow/actions/check-board/`.
- Goal stands: a workflow with possibly automatic bugfixes.

## Position after turn 2
- Executor = mf-watch. It is single-threaded: an action run between polls can
  never overlap a worker run, so "busy" needs no lock file. A cockpit Run button
  writes a request file (like the wake file); the watcher runs it when free =
  "wacht maar even" for free.
- Steps are a script (sh/ps1/console app), not prose. The .md holds frontmatter
  (schedule, command) + a human description. A .md that Claude interprets would
  make the whole action non-deterministic (principle I).
- The action script only needs: sync, decide, write cmd(s) with status ready,
  commit. The watcher dispatches them on the same/next poll; pull/push is
  git_sync, already there.
- Code-changing work always via a cmd (tests, rst, spec-first). Auto bugfix ->
  cmd with `branch:` (existing): worker pushes a branch, human merges. That is
  the safety net for automatic fixes.
- Numbering: at 10 cmds/day 9999 lasts ~3 years; the real cost is lane noise in
  the cockpit, solvable later with a filter. Not a reason for a second path yet.
- Read-only triage could later run `claude -p` inside the action (safe, since
  the watcher serializes), output to the board. Start with one path (cmd).

## User input (turn 3)
- Agreed: actions run only while the project's watcher runs (mf-watch = executor).
- Proposes a second prompts dir `docs/prompts/actions/` for action-made cmds.
  Position: one lane + a `source: <action>` frontmatter field and a cockpit
  filter. A second folder touches the scan, worker id lookup, numbering rule,
  cockpit lane, lint. Would change if action cmds come in dozens a day.
- Asked: does `branch:` create the branch? Yes (worker-run.md step 4): existing
  is checked out, new one is created from `base:` or the default branch; work
  branch pushed, human merges.
- Wants a standard action "git pull/push, solve all conflicts", allowed on a
  dirty tree. Position: conflict resolution yes - a second action kind
  (`prompt:` = claude -p with a fixed prompt, run directly by the watcher,
  safe because serialized; natural trigger: git_sync's conflict notice).
  Dirty tree: no auto-commit of unknown changes; on a worker machine a dirty
  tree is a human mid-edit or a crashed run - committing it hides that.
  Asked the user where their dirty trees come from.

## Premises        (to be confirmed)
1. An action never runs the agent itself; agent work enters the lane as a cmd
   file (draft or ready). Serialization, evidence (rst), retries, specs-first
   come for free; no second agent runner on the same tree.
2. Actions are plain shell commands in `.magnaflow/config.yml`; "git pull/push"
   and "claude with prompt" are not special step types.
3. Prompt injection from files/params = a cmd template the action fills in.
4. Concurrency rule: an action that writes to the tree runs only when no cmd is
   `running`; otherwise skip and log (next tick catches it). No waiting.
5. Logs machine-local (`.magnaflow/actions/<name>.log`), like run/*.log; the
   committed account is whatever the action commits.
6. "Investigate" (bug triage without code change) is a kind of cmd, not an
   action - needs a cmd flavour whose result is an rst with findings.
7. Board sync is project-specific code (the project's own console app), not
   MagnaFlow code.

## Directions      (draft)
A. No new tool: project script + systemd timer/cron writes cmds, commits;
   mf-watch git_sync picks up. Plus kit: an "investigate" cmd convention.
   Small; no button/log in cockpit.
B. `actions:` section; mf-watch runs scheduled ones between polls (single
   thread = natural serialization), cockpit card with Run button (wake-file
   style request) + log tail. Medium.
C. Generic workflow engine (steps, cron, own runner, agent step). Large;
   duplicates the worker; argue against.

## User input (turn 4)
- Dirty trees are rare and trivial. The real pain: a commit lands on the same
  branch during a run -> git_sync rebase conflict the watcher cannot solve;
  Claude Code solves it easily. Maybe preventable some other way (open).
- Agreed: one lane, `source:` field + cockpit filter.

## Chosen
Direction B, shaped:
1. Definitions: `.magnaflow/actions/<name>.md` (in git). Frontmatter:
   `schedule` (interval or nightly time, optional), and exactly one of
   `script:` (a command, resolved like mf-run) or `prompt:` (body = prompt
   template, run as claude -p with agent.command/args). Body = description.
2. Executor: mf-watch, between polls. Single thread = never overlaps a worker
   run; no lock. Due actions run when nothing is dispatching; otherwise next poll.
3. Manual run: cockpit writes `.magnaflow/actions/<name>.request` (wake-file
   style); watcher runs it when free. Queued = "wacht maar even".
4. Guards: skip while a cmd is `running`, or the tree is dirty (log the reason).
   Exception: a conflict action may run on a stopped rebase / failed sync.
5. Agent code work always via the lane: a script action writes cmd files
   (`status: ready`, `source: <action>`, optionally `branch:` for auto-fixes
   the human merges) and commits; git_sync pushes, the next poll dispatches.
6. Logs machine-local `.magnaflow/actions/<name>.log` (+ last result line);
   cockpit Actions card: list, last run, Run button, log tail.
7. Standard kit action: `resolve-conflicts` (prompt): pull --rebase, solve
   conflicts, build/test, push. Triggerable by the git_sync conflict notice.
Why: reuses watch loop, wake-file pattern, mf-run log/resolution, worker,
`branch:`; adds no daemon, no lock, no workflow engine.
