# mf-cockpit v0.4 — completion notes (2026-07-14)

Implements [`ontwerp-v0.4.md`](ontwerp-v0.4.md) in `tools/mf-cockpit/`: write #6, "Add project" —
a `+` on `index.html` that either registers an existing working copy or scaffolds a brand-new one
(git repo, spec kit, optional code template) and seeds the first spec-kit command as a draft.
Mirrors [`v0.3-completion-notes.md`](v0.3-completion-notes.md)'s style.

## What shipped

### Config: `cockpit.new_project`

- `Config/CockpitConfig.cs`: `NewProjectConfig` (`Root`, `SpecKit`, `Templates`) and
  `NewProjectTemplate` (`Name`, `Type` — `"copy"` or `"command"` — `Source`, `Command`, `Args`,
  `Timeout`, default 300s), parsed from `cockpit: new_project: {...}` with the same
  `IgnoreUnmatchedProperties` posture as the rest of the section. `Root`/`SpecKit`/template
  `Source` are normalized with `Path.GetFullPath` (directory paths, same treatment as
  `ProjectEntry.Path`); `Command` is left as-is (may be a bare PATH-resolved name, same posture as
  `ChatConfig.Command`/`RunClientConfig.Command`).
- `CockpitConfig.Load` now also stamps `IsLegacyFileName` onto the returned `CockpitConfig` (it
  already took the flag as a parameter but didn't retain it) — `MagnaflowYmlAppender` needs it at
  request time, after `Program.cs`'s own `LocatePath`/`Load` call has already happened.

### `Config/ProjectRegistry.cs` (new)

A mutable, lock-guarded in-memory project list seeded from `CockpitConfig.Projects` at startup.
Every endpoint that resolves a project by name now goes through `ProjectRegistry` (via
`ProjectResolver.Find(registry, name)`) instead of reading `CockpitConfig.Projects` directly —
`ProjectsEndpoints`, `CommandsEndpoints`, `GitEndpoints`, `RunEndpoints`, `ChatEndpoints`,
`SpecsEndpoints`, `WatchEndpoints`, `ProjectConfigEndpoints` all switched. This is what lets write
#6 register a project and serve it in the same request, with no restart — `CockpitConfig` itself
stays an immutable snapshot of the file it loaded, exactly as before.

### `Config/MagnaflowYmlAppender.cs` (new)

The registration write, as a text edit rather than a parse-and-regenerate (same reasoning as write
#5's raw editor: a regenerated file destroys comments and ordering).

- **Target resolution**, from the already-loaded `CockpitConfig`: `IsLegacyFileName` → refuse
  outright (`LegacyFileRefused`); `ConfigPath` exists on disk → edit it in place; nothing on disk →
  create `magnaflow.yml` in the user config dir (`CockpitConfig.DefaultUserConfigDirectory()`), not
  next to the binary, since that location may not be writable.
- **`ComposeAppendedContent`** (pure, string-in/string-out, directly unit-tested): four shapes,
  found by scanning line indentation rather than assuming a fixed width — an existing `projects:`
  block list (append after the last entry), an inline `projects: []` (replace with a block list), a
  `cockpit:` section with no `projects:` key (insert one as the section's first child), no
  `cockpit:` section at all (append a fresh one, with a blank-line separator if the file already had
  content). Paths are written with forward slashes; the original line-ending style (`\n` vs. `\r\n`)
  is preserved.
- **`AppendProjectAsync`**: writes `<path>.bak` (only if the file already existed), writes the
  edited content, reloads it through `CockpitConfig.Load` and checks the new entry round-trips; on
  any failure restores the `.bak` (or deletes the file if there was nothing to restore) and reports
  `VerifyFailed`. A second overload accepts a composer delegate — the test seam that stands in for
  `ComposeAppendedContent` to prove the restore path with a deliberately broken edit, instead of
  relying on the real composer happening to fail. No locking of its own; the caller (the endpoint)
  holds one lock across scaffold + register.

### `Projects/DirNameSanitizer.cs` + `Projects/ProjectScaffolder.cs` (new)

- `DirNameSanitizer.Sanitize`: trim, strip characters invalid in Windows file names, collapse
  whitespace runs to a single hyphen, collapse repeated hyphens, trim leading/trailing hyphens.
  `IsReservedName` checks the Windows device-name list (`CON`, `NUL`, `COM1`-`9`, `LPT1`-`9`,
  case-insensitive, exact match only).
- `ProjectScaffolder.Validate`: name required → unique among registered projects → root configured
  → sanitized dirname non-empty → not a reserved name → target directory must not exist → template
  name (if given) must exist — the design's own stated order, with the root-configured check
  inserted right before it's needed (dirname/target both depend on it).
- `ProjectScaffolder.ScaffoldAsync`: mkdir → optional template (`copy`: recursive copy of the
  source's contents, skipping a top-level `.git`; `command`: spawn with `{target}`/`{name}`
  substituted into `args`, cwd = target, hard timeout via the existing `IProcessRunner`, non-zero
  exit or timeout fails) → spec kit copy into `docs/spec-kit/` (warning, not failure, when
  unconfigured or missing) → hygiene files where the template didn't already provide them
  (`.gitignore` gets whichever of the three runtime-ignore lines are missing — not skipped whole-
  file if the template's own `.gitignore` is merely incomplete; `.magnaflow/config.yml` gets a
  minimal commented stub only if absent) → `git init` (skipped if the template already left a
  `.git`) + `git add -A` + commit `cockpit: create project <name>` → seed the adopt draft via the
  existing `DraftWriter` (write #1's own code path — title "Adopt spec system", body points at
  `docs/spec-kit/0001-adopt-spec-system.md`). A failed step returns immediately with the captured
  output/error; the directory is never deleted, so a human can diagnose or delete it by hand.

### `Api/NewProjectEndpoints.cs` (new)

- `GET /api/new-project` → `{root?, templates: [names], specKit: bool}` — template `command`/`args`/
  `source` never serialize into the response at all (the DTO only ever holds names).
- `POST /api/projects` → `{mode: "new"|"existing", name, path?, template?}`, one process-wide
  `SemaphoreSlim` gate held across validate + scaffold/resolve + config-append + registry-add, so
  two simultaneous adds can't interleave on `magnaflow.yml`. `mode: "new"`: `ProjectScaffolder`
  validate → scaffold → `MagnaflowYmlAppender` append → `registry.Add` → `SseHub.Broadcast(kind:
  "projects")`, in that order — registration is last, so a failed scaffold or a failed config append
  never leaves a phantom entry (a scaffold-succeeded/append-failed directory is complete and valid
  on disk; "existing" mode picks it up). `mode: "existing"`: path resolved (absolute, or relative to
  `new_project.root` when configured) → must exist and be a directory → duplicate name *or* path is
  a 409 → missing `.git` is a warning in the response, never a rejection → append + register + SSE.
- HTTP status mapping: `NameNotUnique`/`TargetExists`/existing-mode duplicates → 409; every other
  validation failure → 400; a scaffold failure (template exit code, timeout, missing source) → 422
  with the captured output; a config-append failure → 500.

### Frontend

- `index.html`: a `+ Add project` button next to the Projects header, and the same button inside
  the empty-state row (`No projects yet — + Add project`) — with zero projects it's the front door,
  per the design. A `<dialog>` with Existing/New tabs (Existing active by default); New shows a
  template `<select>` (`(empty)` plus every configured name) and a live target-path preview
  (`sanitizeDirName` mirrors `DirNameSanitizer.Sanitize` client-side), and is disabled with an
  explanatory hint when `new_project.root` is missing (`GET /api/new-project`'s `root: null`). On
  success, navigates to `project.html?p=<name>`. The existing SSE handler already re-fetches the
  whole project list on *any* event with no kind filtering, so the new `"projects"` kind needed no
  handler change at all.
- `assets/style.css`: `dialog`/`dialog::backdrop` styling in the existing dark palette,
  `.tab-btn[aria-pressed="true"]` (lava-accent active tab), `#new-target-preview` (monospace).

## Deviations / interpretations worth flagging

- **"No file found anywhere" always targets the user config dir, even for an explicit but missing
  `--config`/`MF_COCKPIT_CONFIG` path.** `CockpitConfig.LocatePath` can't distinguish, from its
  return value alone, "explicit `--config <path>` given, file doesn't exist" from "nothing found
  anywhere, defaulted to the next-to-binary primary path" — both come back as a non-existent path
  with `IsLegacyFileName = false`. ontwerp-v0.4.md states three cases, not four, and its own
  reasoning ("the next-to-binary location may not be writable at all") is specifically about the
  defaulted-primary-path scenario. Implemented literally: any time `ConfigPath` doesn't exist on
  disk (and isn't the legacy filename), write #6 targets the user config dir — including the rare
  case of an explicit `--config` pointing nowhere. Flagging per this fase's own "stop and ask rather
  than guess" clause in case that edge case was meant to write to the explicit path instead.
- **`Root`/`SpecKit`/template `Source` are normalized with `Path.GetFullPath` on load**, which
  ontwerp-v0.4.md doesn't call out explicitly. Without it, a forward-slash YAML value and a
  `Path.Combine`'d target path downstream could disagree on separator style byte-for-byte (harmless
  to the filesystem, but made an early round of integration tests flaky-looking on string
  comparison). Same normalization `ProjectEntry.Path` already gets; `Command` is deliberately
  excluded since it may be a bare PATH-resolved name, matching `ChatConfig.Command`.
- **The scaffold-vs-config-append lock is one process-wide `SemaphoreSlim` in
  `NewProjectEndpoints`, not inside `MagnaflowYmlAppender`.** ontwerp-v0.4.md's "one lock across
  scaffold + register" reads as a single lock spanning the whole write, not just the file edit — so
  the appender itself does no locking (documented in its own summary), and the endpoint holds the
  gate from validation through the SSE broadcast.
- **The corrupted-append `.bak`-restore proof lives in `MagnaflowYmlAppenderTests` (real file I/O,
  not `WebApplicationFactory`), not threaded through the full HTTP stack.** Forcing a genuine
  append failure through the public API without a fragile OS-level trick (e.g. marking the config
  file read-only, which also breaks the restore's own `File.Copy` back onto that same read-only
  path) wasn't practical; the composer-seam test proves the exact mechanism ontwerp-v0.4.md
  describes (`.bak` write → verify → restore) against the real filesystem instead.
- **New-project directories don't get a live `ProjectWatcher`** until the cockpit restarts —
  `ProjectWatchersHostedService` still builds its watcher list once at startup from the initial
  project set. The `"projects"` SSE broadcast on registration (so `index.html` refreshes) doesn't
  need one; only a *newly created* project's own subsequent lane/evidence changes would go
  unnoticed until a restart or manual reload — the same class of gap `ProjectWatcher`'s own doc
  comment already accepts for a project missing a watched directory at startup. Not called out in
  ontwerp-v0.4.md's scope either way; left as a known small gap rather than adding dynamic watcher
  registration for a fase that didn't ask for it.
- **The built-in "empty" template** the design's dialog prose mentions ("the configured templates
  plus a built-in 'empty'") is simply "no template selected" — the frontend always adds an
  `(empty)` option with value `""`, which the backend already treats as "skip the code-template
  step" (`template: null`). No separate backend concept was needed.

  scope") — the project page's watcher line already shows the silence.

- No delete/rename/unregister from the cockpit, no dirname override field, no auto-running the
  adopt prompt — all explicitly out of scope for v0.4.

  exclusion, narrowed but not lifted by this fase's own invariant note).
