# mf-cockpit v0.1 — completion notes (2026-07-13)

Implements [`ontwerp-v0.1.md`](ontwerp-v0.1.md) in `tools/mf-cockpit/`. Mirrors mf-watch's own
post-completion notes style — see
[`../fase4-mf-watch/v0.1-completion-notes.md`](../fase4-mf-watch/v0.1-completion-notes.md).

## What shipped

- `MagnaFlow.MfCockpit` (net10.0, `Microsoft.NET.Sdk.Web` minimal API + Kestrel + static files,
  CliWrap + YamlDotNet — no Spectre.Console.Cli, this is a web app not a CLI). Own minimal
  frontmatter reader (`Prompts/CmdFileLite`, `Prompts/LaneScanner`) — no library reference to
  `tools/worker-controller/` or `tools/mf-watch/` anywhere, same decoupling both of those prove.
- Readers: `LaneScanner` (groups cmd/pln/qa/rst by id, malformed files reported not crashed on),
  `EvidenceReader`/`TailReader` (bounded 200 lines / 64 KB tails for `.magnaflow/<id>/*.log` and
  `mf-watch.log`), `WatchReader` (log tail + lockfile presence), `SpecsBrowser` (path-guarded
  `docs/specs/` browse), `GitClient` (branch/dirty/last-N-commits, read-only).
- Writes: `DraftWriter` — next-free-`NNNN` draft creation and the exact `draft`→`ready` transition
  (409 on any other status), both followed immediately by a real `git add`+`commit`
  (`GitClient.CommitFileAsync`) — the cockpit's only two writes, per the design's invariant.
- Chat: `ClaudeChatRunner` spawns `claude -p --output-format stream-json --verbose
  --permission-mode plan` (always first in argv; `chat.args` can only append, never remove it —
  read-only by construction), harvests `session_id` from the JSON stream, and is resumed via
  `--resume` on the next message. `ChatSessionStore` keeps the per-(project, chatId) session id
  in memory. The API endpoint streams every raw output line to the client as an SSE-style frame
  as it arrives (not buffered to the end), with a hard timeout (config, default 5 min) and kill on
  client disconnect (`ctx.RequestAborted`).
- Live updates: one `FileSystemWatcher` pair per project (`docs/prompts/` → kind `lane`;
  `.magnaflow/` → `watch` for `mf-watch.log`/`.lock` at its root, `evidence` for anything nested
  under `.magnaflow/<id>/`), debounced 500 ms, fanned into `SseHub` and out over `/api/events`
  (project + kind only, no payloads — clients re-fetch).
- Frontend: five hand-written pages (`index`, `project`, `command`, `chat`, `specs`), one shared
  `style.css` (the design doc's exact palette) and `app.js` (fetch/SSE/escaping helpers), and a
  small vendored regex-based markdown renderer (`md.js`) — no build step, no CDN. Banner/logo/ico
  copied from `docs/images/` into `wwwroot/assets/` as build-time `Content` items (`Link=...`), not
  read at runtime from `docs/`.
- Every route from the design's API list is implemented, including the specs catch-all with
  path-escape rejection and the draft-create/ready-flip write endpoints.

## Validation

46 tests (`dotnet test`), all passing:

- **30 unit tests** (`LaneScannerTests`, `TailReaderTests`, `PathGuardTests`, `DraftWriterTests`)
  with fakes for git (`FakeGitClient`), process spawning (`FakeProcessRunner`), and the clock
  (`FakeClock`) — covering lane grouping/malformed handling, next-free-number and slug generation,
  bounded tail reads (line count and byte window), path-escape rejection (rooted paths, drive
  letters, `..`), draft creation, and the exact `draft`→`ready` transition including the 409 cases,
  with a byte-for-byte round-trip check on the rewritten file.
- **14 API integration tests** via `WebApplicationFactory<Program>` against a disposable temp
  project fixture (lane files, evidence, and a **real** git repo — `TempProject.InitGit()` shells
  out to actual `git`): project summary counts, command detail aggregation (cmd/pln/qa/rst +
  evidence + session id), watch tail + lock presence, specs directory/file browse, specs
  path-escape rejection (never leaks content from outside the root), draft creation picking the
  next free `NNNN` (and committing it), ready-flip success + 409 on any non-draft status, and an
  SSE test that mutates a lane file mid-stream and asserts a `{project, kind:"lane"}` frame arrives.
- **2 chat end-to-end tests** against a stub `.cmd` executable (`fixtures/chat-stub.cmd`,
  `fixtures/chat-stub-hang.cmd`), the same swap-the-executable mechanism the worker's and
  mf-watch's own validation used: the stub streams multiple stream-json lines with small delays
  (proving incremental delivery, not one-shot buffering), echoes back whatever `--resume` value it
  received so the second message's reuse of the first message's `session_id` is verified end to
  end, and a hang stub + a tiny configured timeout proves the process is actually killed (completes
  in seconds, not the stub's ~1-hour sleep).
- **Manual smoke testing** against the compiled exe directly (not just `WebApplicationFactory`):
  every endpoint exercised with `curl` against a real temp git repo, including a real
  draft-create → ready-flip → 409-on-repeat round trip with `git log` confirming both bookkeeping
  commits landed.
- **Live browser verification** (`/browse`, per this repo's own CLAUDE.md, not
  `mcp__claude-in-chrome__*`) of all five pages against a seeded fixture project (a `ready`
  command, a `questions` command with an open Q&A, evidence logs, a session id, and two commits) —
  screenshots taken and console checked clean at every step. This is what actually caught most of
  the deviations below; several were invisible to the automated test suite.

## Deviations / interpretations worth flagging

- **`git log --pretty=format:` hangs on Windows.** The most serious finding, caught only by the
  live browser check (the automated test suite's git-info assertions never checked *how long* the
  request took): `git --no-pager log --pretty=format:...` never signals process completion under
  this app's process-spawning setup, even though its output is already fully written and
  captured — every project-summary request silently ate this class's own 30 s timeout before
  falling back gracefully. `--pretty=tformat:` (functionally equivalent, and git's own documented
  choice for scripted/programmatic use) returns in tens of milliseconds. Reproduced identically
  whether the app was launched via a console-less background process or a normal PowerShell
  session, so it is not an artifact of how the app is started. `GitClient` also always passes
  `--no-pager` now (log is the only subcommand here that would otherwise invoke a pager).
- **`ContentRootPath` defaults to the shell's current directory, not the executable's own
  folder.** Also only surfaced once the app was actually run from a directory other than its own
  (exactly how an operator would use it per the README) — `wwwroot` and a same-directory
  `mf-cockpit.yml` silently failed to resolve. Program.cs now pins
  `ContentRootPath = AppContext.BaseDirectory` explicitly, matching `WatchConfig.DefaultPath()`'s
  posture in mf-watch.
- **`Microsoft.NET.Sdk.Web` only copies `wwwroot/**` to the output directory on `dotnet publish`,
  not `dotnet build`.** Since this tool (like its siblings) is meant to be run straight from
  `dotnet build`'s `bin/` output, the csproj promotes that copy to every build via
  `<Content Update="wwwroot\**" CopyToOutputDirectory="PreserveNewest" />`.
- **Frontmatter `status:` rewrite and CRLF.** The surgical single-value rewrite (mirrors
  `MagnaFlow.WorkerController.Prompts.CmdFile.UpdateFrontmatterValue`) originally didn't account
  for a trailing `\r` before the multiline `$` anchor — invisible against LF-only fixture files,
  but broke *every* draft this tool itself creates, since `CmdFileLite.WriteDraft` writes with
  `Environment.NewLine` (CRLF on Windows). Fixed by capturing the optional trailing `\r` in its own
  group and re-appending it, so both line-ending styles survive the rewrite byte-for-byte.
- **Command detail was rendering raw frontmatter as garbled markdown.** `command.html`'s "Command"
  card originally showed the cmd file's *entire* raw content, including the `---` YAML block —
  which the vendored markdown renderer doesn't understand and rendered as a run-on paragraph. Since
  every frontmatter field is already shown structurally above (title/status/attempts/branch/...),
  the API now returns the parsed body only (falling back to the raw file when parsing failed, so a
  malformed cmd is still fully visible for diagnosis).
- **Path-escape testing needed a different technique than a literal `../` in a URL.** Both
  `System.Uri` (used by any standard HTTP client, including the test project's own `HttpClient`)
  and Kestrel itself normalize dot-segments out of a request path before the app ever sees them —
  a real defense-in-depth layer, but it means a literal `..` never reaches `SpecsBrowser`'s own
  guard through an HTTP request. The integration test instead uses a rooted/drive-letter segment
  (which no normalization layer touches) to exercise the app's own `PathGuard` end to end; unit
  tests cover the guard directly with literal `..` strings that never touch a URL at all. The
  design's own acceptance criteria ("expect 400/404, never file content from outside the root") is
  satisfied either way — both a `400` from our own guard and a `404` from upstream normalization
  are valid outcomes, and no scenario ever returned outside content.
- **`ProjectWatchersHostedService.StopAsync` needed to be idempotent.** `WebApplicationFactory`'s
  disposal path invoked it more than once concurrently during integration testing, surfacing as a
  `List<T>` "collection was modified" exception. Guarded with an `Interlocked` flag — reasonable
  hardening for any host lifecycle, not just tests.
- **Disabled secondary buttons had no visual affordance.** `chat.html`'s "make this a command"
  button (disabled until a reply arrives) was visually identical to an enabled button, because
  `.secondary`'s own color/background rule had equal CSS specificity to the generic
  `button:disabled` rule and won on source order. Added `button.secondary:disabled` explicitly.
- **`GitInfo.Commits` was built but never surfaced.** The design's "git info" (`project.html`)
  calls for "last N commits", not just branch/dirty — `ProjectSummaryDto` didn't originally expose
  it. Added `GitCommits` to the DTO and a short list under the branch/dirty line in `project.html`.
- **Stale-`running` threshold**: the design doesn't pin one. Used 15 minutes since the newest of
  `claude.log`/`build.log`/`test.log`'s last-write time (falling back to the cmd file's own mtime
  when no evidence directory exists yet), recomputed fresh on every request — the cockpit has no
  daemon memory the way mf-watch's own in-process stale tracking does.
- **Chat streaming implementation detail**: `CliWrapProcessRunner` invokes the per-line callback
  synchronously under its own lock as output arrives; the chat endpoint blocks on
  `WriteFrameAsync(...).GetAwaiter().GetResult()` inside that callback to flush each line to the
  HTTP response immediately. This is what makes the stream arrive incrementally instead of all at
  once at process exit — acceptable for a low-throughput chat UI, flagged here since it's a
  deliberate sync-over-async choice, not an oversight.
- **`--config` / `MF_COCKPIT_CONFIG`**: the design says config is next to the binary or via
  `--config`; an `MF_COCKPIT_CONFIG` environment variable was added purely so
  `WebApplicationFactory` (which re-executes `Program.cs`'s top-level code in-process rather than
  passing test-controlled argv) can redirect config path in integration tests. Not part of the
  design doc, but doesn't change any documented behavior for real usage.

## Not done / left for later

- No live Claude Code validation was performed for the chat — only the stub `.cmd` executable
  (same caveat mf-watch's and the worker controller's own completion notes flag for their
  respective stub-based validations).
- Further action buttons (git commit/push of hand-edits, new branch, retry an aborted cmd, answer
  qa files in the browser), auth/HTTPS, historical metrics/charts, mobile layout, and tray/daemon
  packaging are all explicitly out of scope per the design's own "Not in scope (v0.1)" list.
- The chat's "busy indicator" and escalate-to-draft flow were verified via code review and a
  static fixture (a `running` count of 0 correctly hides the banner; a disabled button correctly
  enables once a reply arrives is implied by the JS but wasn't exercised against a live agent
  reply in the browser — only against the stub in the automated e2e tests).
- No load/perf testing beyond the pathological `git log --pretty=format:` case found above; the
  bounded-tail guards (200 lines / 64 KB) are unit-tested but not stress-tested against a
  multi-megabyte real `claude.log`.
