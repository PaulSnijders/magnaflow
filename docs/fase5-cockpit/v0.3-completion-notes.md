# mf-cockpit v0.3 — completion notes (2026-07-14)

Implements [`ontwerp-v0.3.md`](ontwerp-v0.3.md) in `tools/mf-cockpit/`, plus the one `tools/mf-run/`
change it carries along (`status --json`). Mirrors [`v0.2-completion-notes.md`](v0.2-completion-notes.md)'s
style.

## What shipped

### mf-run: `status --json`

- `Runtime/StatusJson.cs`: serializes `IReadOnlyList<ServiceStatusEntry>` to the design's
  `[{name, running, pid?, url?}]` shape — camelCase, null `pid`/`url` omitted via
  `JsonIgnoreCondition.WhenWritingNull`.
- `Program.cs`: a `--json` flag, parsed alongside `--project`; only changes `status`'s own output
  branch — exit-code semantics (`0` iff everything asked about is running) are untouched. The
  pre-existing "no services configured" short-circuit (which fires for every verb before targets
  are computed) now also honors `--json` for `status`, printing `[]` instead of the prose message —
  otherwise a project with no `run:` block would break a script piping `status --json` into a JSON
  parser.
- Tests: `StatusJsonTests.cs` (4 new) — running-with-pid-and-url, stopped-with-nulls-omitted,
  empty-list, order-preserved. mf-run's suite: 33/33 (was 29).

### Cockpit: the Run card

- `Config/CockpitConfig.cs`: `RunClientConfig` (`Command` default `mf-run`, `Timeout` default 60s)
  and a `Run` property, parsed from `cockpit: run: {command, timeout_seconds}` — same seam shape and
  same `IgnoreUnmatchedProperties`/legacy-detection posture as `ChatConfig`.
- `Config/ProjectConfigReader.cs` (new): read-only parsing of the *project's own*
  `.magnaflow/config.yml`, own implementation (no reference to
  `MagnaFlow.WorkerController.Config.ProjectConfig`). Four entry points: `ComputeHash` (SHA-256 hex
  of the raw content, the optimistic-concurrency token), `Summarize` (build/test commands, max
  attempts, run-service names — tolerant of a broken file, returns defaults), `ReadRunServiceNames`
  (null when there is no `run:` key at all — the "configured: false" signal — vs. a possibly-empty
  list when `run:` is present; the cockpit never spawns mf-run for a project that plainly isn't
  using it), and `Validate` (a real YAML syntax error is a rejection with line/column from
  YamlDotNet's own `Mark`; an unrecognized top-level key is only ever a warning).
- `Infrastructure/IRunClient.cs` + `MfRunClient.cs`: the Run card's only door to the outside world.
  `StatusAsync`/`StartAsync`/`StopAsync`/`RestartAsync` each shell out to `run.command <verb>
  [service] --project <root>` (`status` additionally passes `--json`) via the existing
  `IProcessRunner` seam — no PID or process-tree logic in the cockpit at all, exactly the invariant.
- `Api/RunEndpoints.cs`: `GET /api/projects/{name}/run` (the `configured: false` shape when there's
  no `run:` block; otherwise shells out and passes the parsed JSON through, with a `RunStatusDto`-
  level `Error` string if mf-run's own output doesn't parse as JSON), `POST .../run/start|stop` (all
  services, service = null), `POST .../run/{service}/start|stop|restart` (404 when the name isn't
  in the project's own config), and `GET .../run/{service}/log` (bounded tail of
  `.magnaflow/run/<service>.log` via the existing `TailReader`).
- `Api/ProjectConfigEndpoints.cs`: write #5. `GET .../config` (content + hash + parsed summary),
  `PUT .../config` enforcing, in the design's own stated order, hash match (409) → YAML parses (400,
  with position) → size cap (400, 256 KB) → write + `git add` + `git commit -m "cockpit: edit
  config"`.
- `Live/ProjectWatcher.cs`: `ClassifyMagnaflow` gains a `"run"` kind for anything under
  `.magnaflow/run/` (both the directory-creation event and file events inside it), fanned out over
  the existing SSE hub — no new transport, just a new coarse kind clients can react to.
- `Program.cs`: registers `RunClientConfig`/`IRunClient`/`MfRunClient` and maps the two new endpoint
  groups.

### Frontend

- `project.html`: a Run card (hidden entirely when `configured` is false or `services` is empty) —
  per service a colored dot, running/stopped text with PID, the `url` as a link, an expandable log
  tail, and Start/Stop/Restart buttons; a header row with Start all/Stop all. Every button POSTs and
  re-renders from the response; action results (exit code, output, timed-out) render inline per
  service or in the card's own error line for the all-services actions. A `#config-link` was added
  to the page's nav, next to Specs/Chat.
- `index.html`: a `Run` column, one `k/n` chip per project row, fetched asynchronously (its own
  `GET .../run` spawns a process, same reasoning as the existing git-branch cell) so it never delays
  the fast counts/attention render.
- `config.html` (new page): a read-only summary card (build/test commands, max attempts, run
  services) plus a raw `<textarea>` YAML editor and Save button; a warning banner when any lane
  command in the project is `status: running` (checked via the existing
  `GET .../commands`, not a new endpoint — this is about a *worker run*, not an mf-run *service*).
  Save round-trips the hash and surfaces the server's warnings/errors inline; no client-side YAML
  validation — the server is the only parser.
- `assets/style.css`: `.run-service`/`.run-dot`/`.run-result` rules, `dl.config-summary`, and
  `#config-editor` (monospace, resizable, `white-space: pre`).

- **Full suites green**: mf-run 33/33, mf-cockpit 127/127 (was 91 before this fase; +36).
- **Live browser verification** (`/browse`, per this repo's CLAUDE.md): a disposable project +
  `magnaflow.yml` pointing `cockpit.run.command` at the real compiled `MagnaFlow.MfRun.exe`
  (Release), with a `run.services` entry whose `command` is a small looping `.cmd` stub (echoes a
  timestamped line every ~2s, mirroring the shape of mf-run's own v0.1 E2E fixture without
  recreating its tree-kill scenario, which mf-run's own suite already proved). Walked:
  - `project.html`: Run card renders with the dot/url/buttons; clicking Start flips the dot to
    green with a PID within ~3s, no manual reload; the log toggle shows the stub's real output;
    Stop flips the dot back to red.
  - `index.html`: the new `Run` column shows `0/1` for the demo project.
  - `config.html`: summary card and editor populate from the real file; saving with a deliberately
    broken YAML edit (`broken: [not valid`) renders `400 Bad Request: line 15, column 1: ...` inline
    without touching the file; fixing it and changing `max_attempts` saves successfully, the summary
    updates, and `git log` in the fixture confirms a `cockpit: edit config` commit with exactly that
    line changed and the leading comment/other lines untouched; flipping the one lane command's
    frontmatter to `status: running` (by hand, then reverted) showed and hid the warning banner.
  - Console was clean throughout except the one console error Chrome itself logs for the
    deliberately-triggered 400 fetch response (the bad-YAML test) — expected, not a bug.
  - **Bug found and fixed during this pass**: the SSE `"run"` event fires continuously while a
    service is actively writing its log (every debounced burst of file writes), and `loadRun()`
    re-rendered the whole card via `innerHTML`, which silently collapsed any log tail the human had
    just expanded. Fixed with an `expandedRunLogs` `Set` in `project.html` that survives across
    `renderRunServices()` calls — re-render now re-opens (and refreshes) any log the human had
    expanded instead of resetting it. Confirmed fixed live: expanding the log, then triggering a
    re-render via Stop, left the log open with fresh content.

## Deviations / interpretations worth flagging

- **The service-log-tail endpoint (`GET /api/projects/{name}/run/{service}/log`) is not in
  ontwerp-v0.3.md's own "API" bullet list**, but the same design's "The Run card" prose explicitly
  requires it ("an expandable bounded tail of `.magnaflow/run/<service>.log` — the existing bounded
  tail reader"). Added it as the obvious missing piece rather than stopping to ask, since the prose
  is unambiguous and the endpoint is a thin, guard-free wrapper around the already-existing
  `TailReader` (no new capability, no new risk). Flagging per this fase's own "stop and ask" clause
  in case the omission was deliberate rather than an oversight.
- **`ReadRunServiceNames` null-vs-empty-list semantics**: null only when the project's
  `.magnaflow/config.yml` has no `run:` key at all (or doesn't exist, or fails to parse) — the
  "configured: false" shape, which exists specifically so the cockpit never spawns mf-run for a
  project that plainly isn't using it (this matters most for `index.html`'s per-row chip, fetched
  for every configured project). A `run:` block present with an empty or absent `services:` list is
  "configured" (non-null, empty list) — visually identical to "not configured" either way, since
  both hide the card/show `-` for the chip, per the design's own "No services configured → no card."
- **PUT validation order followed literally**: hash match → YAML parses → size cap, exactly as
  ontwerp-v0.3.md states it — meaning an oversized-but-parseable payload is YAML-parsed before being
  rejected for size. Confirmed this is what the design says (not just what "made sense") by a
  dedicated test proving hash-drift-beats-broken-YAML; ASP.NET's own default Kestrel request-body
  ceiling (~28 MB) is the outer backstop against a truly pathological payload reaching the parser at
  all.
- **`Validate()` and `Summarize()` each parse the YAML separately** (`Validate` into a raw
  `Dictionary<string, object?>` to see literally every top-level key; `Summarize` into a typed DTO
  with `IgnoreUnmatchedProperties`, which would otherwise silently swallow the very keys `Validate`
  needs to warn about). Two parses per `PUT`; not worth a shared intermediate representation at this
  file size (256 KB cap) and call frequency (human-paced saves).
- **`run.command`'s cockpit-side seam has no `args` field**, unlike `chat.command`/`chat.args`. The
  real `claude` binary needs assorted flags chat.args exists to append; mf-run's own CLI is four
  verbs plus `--project`/`--json`, with no known need for extra passthrough flags — added only
  `command` and `timeout_seconds` per KISS, extendable later if a real need shows up.
- **Live-validation fixture used a `.cmd` loop, not a compiled stub service.** Sufficient for what
  this fase needed to prove (the cockpit's UI/API wiring against mf-run's real status/start/stop
  contract); mf-run's own process-tree/PID-reuse correctness was already end-to-end validated in
  `docs/fase6-mf-run/v0.1-completion-notes.md` and wasn't worth re-proving here.

## Not done / left for later

- No health check or URL probing on the Run card — "the dot means the process is alive", mf-run's
  own v0.1 contract, unchanged.
- No structured "add a service" form for `config.html` — raw YAML only, exactly as scoped
  ("Not in scope (v0.3)").
- Machine-config (`magnaflow.yml`) editing remains out of scope — the cockpit editing its own
  config is self-surgery, per the design's own "Not in scope" list.
- No service-log live-streaming — the bounded tail plus the SSE-triggered refresh (now correctly
  preserving the human's expand/collapse choice) is the whole mechanism, per the design.
- Write #4 ("commit all") is unaffected by this fase, already shipped.
