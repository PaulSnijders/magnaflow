# mf-cockpit v0.2 — completion notes (2026-07-13)

Follow-up commands + polish. Extends `tools/mf-cockpit/` per the v0.2 build prompt; also touches
`tools/worker-controller/` and `tools/mf-watch/` (id grammar only — see below). Mirrors
[`v0.1-completion-notes.md`](v0.1-completion-notes.md)'s style.

## What shipped

### Follow-up commands (write #3)

- **Id grammar widened** from `\d{4}` to `\d{4}[B-Z]?` in all three tools that parse or validate
  lane ids — each keeps its own copy, no shared library:
  - `MagnaFlow.WorkerController.Prompts.PromptScanner` (`IdPattern`, `CmdFileName`,
    `SiblingFileName`) and `CmdFile` (`Number`/`Name` splitting, the title fallback — both now
    locate the actual hyphen via a small `IdShape.NumberLength` helper instead of hardcoding a
    4-character offset, since a follow-up's prefix is 4 or 5 characters).
  - `MagnaFlow.MfWatch.Prompts.PromptStatusScanner` (`CmdFileName` only — mf-watch never
    decomposes an id into number/name, it only ever compares the whole string).
  - `MagnaFlow.MfCockpit.Prompts.LaneScanner` (`CmdFileName`) and `CmdFileLite`
    (`Number`/`Name`/title fallback, same `IdShape` pattern as the worker controller's own copy).
  - `PromptScanner.IdPattern`'s widening also transparently widens what
    `ResumeResolver.Resolve` will treat as "this `resume:` value is another command's id" —
    unchanged code, correct new behavior, verified by reading the source rather than assumed.
- **`LaneScanner.NextFreeSuffix(projectRoot, baseNumber)`**: next free letter (B, then C, ...)
  across every file sharing a 4-digit base number, cmd or sibling, well-formed or not — same
  never-collide posture as `NextFreeNumber`. `NextFreeNumber` itself needed no change: its regex
  already requires the hyphen immediately after 4 digits, so a suffixed file is invisible to it by
  construction (the base number is still accounted for via the plain sibling that must already
  exist for a follow-up to exist at all).
- **`DraftWriter.CreateFollowUpAsync(projectRoot, parentId, feedback, slug?)`**: looks up the
  parent (`ParentNotFound` → caller returns 409, per the build prompt's explicit choice of status
  code over the more usual 404), allocates the next letter for the parent's *base number* — so
  continuing a follow-up itself (`0005B`) still shares `0005`'s own letter sequence and produces
  `0005C`, not a nested scheme — copies `branch`/`base`/`group`/`specs` from the parent verbatim,
  and sets `resume:` to the parent's own recorded session id read from
  `.magnaflow/<parentId>/session.yml` (`EvidenceReader.ReadSessionId`, new public entry point next
  to the existing private one `Read` already used). A parent with no recorded session still gets a
  draft, just without `resume:`, and the API response carries a `warning` string the frontend
  surfaces via `alert()`.
- **`CmdFileLite.WriteDraft`** gained optional `branch`/`base`/`resume` parameters (default null,
  so the existing plain-draft call site is untouched) to write the extra frontmatter a follow-up
  needs.
- **API**: `POST /api/projects/{name}/commands/{id}/follow-up` (body `{feedback, slug?}` →
  `{id, path, resumeSet, warning}`), `GET /api/config` (`{chatEnabled}` — the frontend needed a way
  to know whether to link to chat.html at all, and exposing the whole config felt like more than
  the browser needs).
- **Frontend**: `project.html`'s lane table indents a follow-up row under its parent with a small
  `↳` marker (CSS only, `tr.followup-row`); `command.html` gained a "continue on this command" card
  (feedback + optional slug), shown only when status is `done`/`aborted`, that POSTs and redirects
  to the new draft's own page — putting it right next to the chat link per the prompt's "both one
  click from a finished command."

### Polish

- **Pretty-print JSON logs**: `Cockpit.logView(el, toggleButton)` (new in `app.js`) detects lines
  that parse as a single JSON object/array (as in `claude.log`'s stream-json) and renders them as
  a collapsible `<details>` with a one-line summary (`type:subtype` when present, else a truncated
  `JSON.stringify`) and the pretty-printed body inside; non-JSON lines render as plain text lines.
  A per-log "Raw"/"Pretty" toggle button switches the whole block to the original plain-text tail
  and back; the bounded-tail guards (200 lines / 64 KB) are unchanged — this only changes how the
  same already-bounded lines are displayed.
- **Clickable breadcrumb**: `Cockpit.renderBreadcrumb(el, segments)` replaces every page's static
  `<h1>` title text; the current page's segment stays plain text, everything before it links up
  the hierarchy (cockpit → project → command/chat/specs). `specs.html` keeps its own separate
  in-card breadcrumb for the spec sub-path — a different concern (browsing inside `docs/specs/`,
  not navigating between cockpit pages).
- **Chat discoverability**: `project.html` already linked to chat in v0.1; `command.html` did not.
  Both now gate the link on the new `GET /api/config`'s `chatEnabled` (`project.html`'s existing
  link wasn't gated on this in v0.1 either — now is, for consistency).

## Deviations / interpretations worth flagging

- **`resume:` is the parent's raw session id, not the parent's own id.** `ResumeResolver` supports
  both forms (an id-shaped value re-resolves that command's own session at run time; anything else
  is a raw session id passed through verbatim) — the build prompt's phrasing ("`resume:` set *from*
  the parent's session.yml") and its own framing ("if it expects something other than a raw session
  id, follow the worker") both point at the raw-id path as the intended one, so that's what's
  written. Chained follow-ups still work correctly either way since `EvidenceReader.ReadSessionId`
  is read from whichever specific command was clicked, not necessarily the lineage's root.
- **409, not 404, for an unknown follow-up parent** — an unusual choice for "not found", but it's
  explicit in the build prompt and keeps this write's error vocabulary consistent with the
  ready-flip write's own 409-for-wrong-state.
- **No backend enforcement that the parent must be `done`/`aborted`.** The build prompt frames this
  as a UI affordance ("sensible only for terminal statuses") on the button, not a stated validation
  rule with its own test case — the required test list only covers unknown-parent (409) and the
  missing-session warning path. Left unenforced server-side; a human could still curl a follow-up
  off a `ready` parent. Flagging this as a judgment call rather than an oversight.
- **Follow-up letter allocation is scoped to the base number, not the clicked ancestor.**
  Continuing `0005B` itself allocates `0005C` (shares `0005`'s sequence), matching the build
  prompt's own worked example (`0005 → 0005B → 0005C`) rather than a nested/branching scheme.
- **Default follow-up slug** (when the optional slug field is left blank) reuses the parent's own
  name slug verbatim (e.g. `0005B-fix-lava` from `0005-fix-lava`) rather than deriving one from the
  feedback text — keeps the filename immediately recognizable as "the same feature, continued";
  the build prompt left this default unspecified.
- **Chat gating retrofit**: `project.html`'s chat link existed in v0.1 without checking
  `chat.enabled`. Since this session added the only mechanism to check it (`GET /api/config`), that
  existing link now also respects the flag — a fix opportunistically bundled with the "add it to
  command.html too" ask, not a separate feature.

## Not done / left for later

- No live Claude Code validation of an actual `--resume <session-id>` continuation — only the
  file-format contract (the written `resume:` value and the worker's own `ResumeResolver` source)
  was verified; this session didn't run a real two-round agent conversation end to end.
- Suffix exhaustion (`B..Z` all taken, 25 follow-ups on one lineage) returns a 409 from
  `DraftWriter`/the API but has no dedicated test or UI messaging beyond the generic error string —
  an edge case far outside any realistic follow-up chain length.
- The report card's own `# Report` heading rendering slightly oddly next to the card's `REPORT`
  label (pre-existing from v0.1, not touched here) is still there — out of scope for this prompt.
- Further v0.x action-button candidates (git commit/push of hand-edits, new branch, retry an
  aborted cmd, answer qa files in the browser) remain out of scope, per the design's own "Not in
  scope" list — follow-up commands were the one new write this version added.
