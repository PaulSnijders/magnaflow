# mf-watch v0.1 — completion notes (2026-07-10)

Implements [`ontwerp-v0.1.md`](ontwerp-v0.1.md) in `tools/mf-watch/`. Mirrors the Worker
Controller's own post-completion notes style — see
[`v0.2-completion-notes.md`](../fase2-worker-controller/v0.2-completion-notes.md).

## What shipped

- `MagnaFlow.MfWatch` (net10.0, CliWrap + YamlDotNet — no Spectre.Console.Cli: a single-purpose
  daemon with three flags doesn't need a multi-command CLI framework, and adding one would be a
  dependency without a concrete need).
- One poll cycle (`WatchLoop.PollOnceAsync`): optional `git pull`, scan `docs/prompts/` for
  `status: ready`, dispatch `mf-worker` sequentially one command at a time, optional `git push`,
  notify. Own minimal `PromptStatusScanner` (id/status/title only) — deliberately not a reference
  to the worker controller's `CmdFile`/`PromptScanner`, since mf-watch "knows frontmatter statuses
  and exit codes, nothing of internal formats" (design invariant); no library coupling to
  `tools/worker-controller/` anywhere in the codebase.
- Adaptive backoff (`BackoffScheduler`): pure state machine over an injected `IClock` — stays at
  `interval_min` through any activity or through empty polls still inside `idle_grace`; once grace
  has elapsed with no activity, doubles per empty poll up to `interval_max`; any activity resets
  both the interval and the idle window.
- `notify_command` shell-template channel (`{title}`/`{message}`), fired alongside the always-on
  console/log line, at exactly the moments the design calls "the human is at bat": run finished
  (`done`/`aborted`), `questions` raised, or an error (git failure, worker exited unexpectedly, or
  a `running` command found that mf-watch did not itself just leave that way).
- Stale-`running` detection: notified once per command per mf-watch process lifetime (in-memory
  set, v0.1 scope — resets on daemon restart), whether discovered on startup or because mf-watch's
  own dispatch left a command stuck in `running` (worker crashed without transitioning status).
- Cross-instance lockfile (`.magnaflow/mf-watch.lock`, exclusive file handle — OS releases it the
  instant the process dies however it died, no separate PID-liveness check needed); applies to
  `--once` too, so a scheduler-triggered run correctly refuses to overlap a live daemon.
- Logging: console always; `.magnaflow/mf-watch.log` appended alongside the worker's own
  `.magnaflow/<id>/` evidence, one line per poll/run/notify/error event.
- `--once`: single poll cycle, exit 0. `--project`/`--config` flags; config defaults to
  `mf-watch.yml` next to the binary, and is entirely optional (every field has a default).

## Validation

- 36 unit tests (`dotnet test`), all passing, with fakes for git (`FakeGitClient`), process
  spawning (`FakeProcessRunner`, which can run a delegate in place of a real process so tests can
  simulate the worker mutating the cmd file's status), and the clock (`FakeClock`) — the backoff
  logic is exercised entirely by advancing a fake clock and calling `RecordPoll`, no real sleeping
  anywhere in the suite.
- End-to-end validation against the real compiled `MagnaFlow.MfWatch.exe`, real git, and a
  disposable project, using a stub `mf-worker` replacement (`worker.command` pointed at a small
  throwaway console app) — the same swap-the-executable mechanism the worker controller's own
  validation used for `agent.command` (FR-019). The stub receives the exact
  `run --project <root> <id>` argv mf-watch composes, flips the target command's `status: ready`
  to `status: done`, and (best-effort) `git add`+`git commit`s that change, so a realistic
  bookkeeping commit exists for the push scenario:
  - **ready → run → done**: a seeded `0001-hello` (`status: ready`) was dispatched by `--once`;
    the stub ran, the command file's status became `done`, the console/log line reported
    `worker finished (exit 0); status is now 'done'`, and exit code was 0.
  - **empty poll**: a second `--once` against the same project (nothing left `ready`) produced no
    executable spawn and exit 0.
  - **lockfile refusal**: a second process (a PowerShell background job, not just an in-process
    check) opened `.magnaflow/mf-watch.lock` exclusively; a concurrent `--once` printed
    `another instance is already running...` and exited 3.
  - **`git_sync` pull/push**: a bare "remote" repo plus two clones (`local`, with `git_sync: true`,
    and `other`, simulating a second machine) — `other` committed and pushed a new ready command
    (`0002-world`) to the shared remote's `main`; `--once` against `local` logged
    `git pull: new commits`, dispatched and completed `0002-world`, logged `git push: ok`, and
    `git log --oneline` on the bare remote afterward showed the stub's bookkeeping commit
    identically on both `local` and the remote — confirming the full pull → dispatch → push
    round-trip against real git, not just the fakes.

## Deviations / interpretations worth flagging

The design doc describes the poll cycle and guards but doesn't spell out every mechanical detail;
where it was silent, the call made and the reasoning:

- **Worker invocation shape**: mf-watch always spawns
  `<worker.command> run --project <projectRoot> <id>` plus any configured `worker.args` appended —
  derived directly from `mf-worker run <cmd-id> [--project <path>]`'s actual CLI (`RunCommand.cs`
  in the worker controller), not stated explicitly in the design doc.
- **Notification categorization**: after a dispatch, mf-watch re-reads the command's status and
  only trusts exit codes 0/1 (the worker's own `Success`/`TaskFailed` — both legitimate terminal
  outcomes per the worker's own exit-code contract) combined with a resulting status of
  `questions`/`done`/`aborted`. Any other combination (unexpected exit code, or status that didn't
  transition) is reported as an error, not silently treated as "done". This reconciles the design's
  two notification categories ("run finished done/aborted" vs. "errors: worker non-zero exit")
  with the fact that `aborted` itself is exit code 1 on the worker's own contract.
  `docs/fase4-mf-watch/ontwerp-v0.1.md` doesn't spell out this reconciliation explicitly — not a
  contradiction, just a judgment call worth flagging.
- **Config location default**: `mf-watch.yml` next to the binary (`AppContext.BaseDirectory`), as
  the design states, is separate from a target project's own `.magnaflow/config.yml` — mf-watch
  can point `--project` at any project without that project needing to know about mf-watch at all.
- **Push is unconditional when `git_sync`**, exactly as the design's step 4 states, independent of
  whether that poll's pull or dispatch produced activity — a no-op push is cheap and this avoids
  a subtle "did we forget to push a bookkeeping commit from two polls ago" gap.

## Not done / left for later

- No live `mf-worker` validation was performed — only the stub executable. The stub validates the
  full mf-watch/git/filesystem contract (argv shape, status re-read, commit/push plumbing) but not
  a real worker run's actual duration, output volume, or the `questions` status path end-to-end
  (unit-tested via `WatchLoopTests`, not exercised against the compiled binary).
- Stale-`running` notification state is in-memory only (v0.1 scope, matching the design's
  "deliberately headless" stance) — a daemon restart forgets which stale commands it already
  surfaced and will notify about them again once.
- No graceful-shutdown test for the daemon loop's `Ctrl+C` handling (`Console.CancelKeyPress`) —
  implemented per the general expectation that a long-running daemon should release its lockfile
  cleanly, not called out as a design or task requirement, and not covered by `--once` validation
  since `--once` never reaches the sleep/loop path.
