# mf-run v0.1 — completion notes (2026-07-14)

Implements [`ontwerp-v0.1.md`](ontwerp-v0.1.md) in `tools/mf-run/`, plus the two worker-controller
hook points and the mf-spec repo-hygiene updates the design carries along. Mirrors mf-watch's own
completion-notes style — see
[`v0.1-completion-notes.md`](../fase4-mf-watch/v0.1-completion-notes.md).

## What shipped

- `MagnaFlow.MfRun` (net10.0, YamlDotNet only — no CliWrap, no Spectre.Console.Cli: four verbs
  with plain top-level-statement arg parsing, matching mf-watch's own precedent for "not enough
  surface to justify a CLI framework").
- `ServiceManager`: start/stop/restart/status over `run.services` from the target project's own
  `.magnaflow/config.yml`. Start order = config list order; stop (and the stop half of restart) =
  reverse order. Start is a no-op (exit 0) when the recorded PID's OS start time still matches;
  stop is idempotent and cleans up stale PID files without ever killing a recycled PID; a start
  failure reports the log tail either for an immediate exit or for one that shows up only after
  the ~2s liveness wait.
- `IProcessSpawner`/`SystemProcessSpawner`: a **new** seam, deliberately not mf-watch/worker-
  controller's `IProcessRunner` (which runs a command and waits for it to finish). mf-run needs to
  *start and forget* a process that must survive mf-run's own exit, with stdout/stderr already
  landing in a file — piping through mf-run's own process (what `IProcessRunner`/CliWrap do) would
  break the moment mf-run exits. Real spawning shells out (`cmd /d /s /c` on Windows, `/bin/sh -c
  exec` on Unix) purely for the shell's own `>`/`2>&1` file redirection — the same technique
  mf-watch's `RunShellAsync` uses for user commands, applied here because it's the only way to get
  OS-level (not piped) redirection without platform-specific P/Invoke.
- `IClock`/`SystemClock`/`FakeClock`: extended beyond mf-watch's version with a `Delay` method (not
  just `UtcNow`), so the ~2s start-liveness wait is fakeable in tests without a real sleep — the
  fake's `OnDelay` hook lets a test mutate the fake process table at exactly the moment
  `ServiceManager` would next check on it.
- `PidFile`: plain two-line text (PID, then the process's start time as round-trip ISO-8601) —
  `cat` suffices, per the design.
- `RunConfig`: reads only the `run:` key from `.magnaflow/config.yml` (`IgnoreUnmatchedProperties`
  for everything else, same technique `WatchConfig` uses for its own separate file); validates
  duplicate service names and a missing `command:` field at load time. Whether the command's
  *path* actually exists on disk is checked at start time instead (in `ServiceManager`), not at
  config-load time — the exe may not exist yet if the project hasn't been built.
- CLI (`Program.cs`): `mf-run <start|stop|restart|status> [service] [--project <path>]`. A project
  with no `run:` services prints `no services configured` and exits 0 for every verb — a console
  app is the normal case here, not an error.

## Validation

- 29 unit tests (`dotnet test`), all passing, with `FakeProcessSpawner` (a fake OS process table —
  `Start`/`GetProcess`/`KillTree` — that tests mutate directly to simulate a process dying,
  recycling a PID, or a kill failing) and `FakeClock`. Covers PID-file round-tripping and malformed
  files, config validation (duplicate names, missing command, missing/empty `run:` block), the
  start-time staleness guard on both start and stop, start/stop/restart ordering, the no-op
  already-running path, and both start-failure shapes (dies immediately vs. dies during the
  liveness wait) with their log tails.
- End-to-end validation against the real compiled `MagnaFlow.MfRun.exe` and a disposable project,
  using a small compiled stub service (stays alive in a loop, spawns one child process of its own
  — the locked-port shape) and a `.cmd` batch file that exits immediately with an error:
  - **start writes the PID file; `status` and the OS agree it's running** — `Get-Process` on the
    recorded PID showed the process alive, and both the stub's own PID and its child's PID were
    live in the OS process table.
  - **stop kills parent and child** — after `mf-run stop`, `Get-Process` on both the recorded PID
    and the child's PID it had printed to its log returned nothing; the whole tree was gone, not
    just the top of it.
  - **stop again is a no-op, exit 0** — `web: not running`, no kill attempted.
  - **a hand-written stale PID file (wrong start time) is cleaned up without killing anything** —
    `web: stale pid file removed (was not actually running)`, exit 0, no OS process touched.
  - **a service whose command exits immediately reports a start failure with a log tail** — the
    `.cmd` stub's own `echo` output ("FATAL: port already in use") came back verbatim in mf-run's
    own stdout under `log tail:`.
  - Also exercised: starting multiple services together with one failing (the other still starts;
    overall exit code 1), restarting a single already-running service, and a full `stop` sweep
    across a mixed running/stopped/never-started set — all left zero stray OS processes behind.
- Worker-controller integration validated against the real compiled `MagnaFlow.WorkerController.exe`
  with both `agent.command` and `run.command` pointed at small compiled stubs that each append one
  line to a shared sequence log — the append order *is* the call order, since `mf-worker` never
  runs two of these concurrently:
  - **happy path**: `AGENT` (plan) → `MFRUN stop` → `AGENT` (implementation, resumed session) →
    `MFRUN start`, in that exact order; final status `done`.
  - **stop failure**: stub `mf-run stop` exited 1 → the run stopped at exactly one `AGENT` call and
    one `MFRUN stop` call (implementation, and `MFRUN start`, never ran), exit code 3
    (`PreconditionRefused`), the command file's `status:` was back to `ready` with `attempts: 0`,
    and `git status --porcelain` was empty — the plan-phase evidence and the revert both landed in
    one clean bookkeeping commit (`mf-worker: <id> -> ready (... stop failed)`).
  - **start fires after `aborted` too**: build forced to fail every attempt → `MFRUN start` still
    appears as the last line in the sequence log, after the terminal `aborted` status was written.

## Deviations / interpretations worth flagging

- **Command/workdir path resolution**: both `command` and `workdir` are resolved relative to the
  **project root**, not to each other — the design's own example (`command:
  src/MyApp/bin/Debug/net10.0/MyApp.exe` alongside `workdir: src/MyApp`) only makes sense under
  that reading (nesting `command` under `workdir` would look for
  `src/MyApp/src/MyApp/bin/...`). Not spelled out explicitly in the design.
- **`ProcessStartInfo.ArgumentList` vs. `Arguments` on Windows**: discovered live during E2E
  validation, not anticipated from the design or from mf-watch's precedent. `ArgumentList` applies
  .NET's own argv-style escaping to each element; when the element is itself a full shell command
  line containing embedded quotes (the redirected `"<exe>" > "<log>" 2>&1` string), that escaping
  corrupts the quotes cmd.exe needs for its own `/S`-mode re-parsing, and every redirected spawn
  failed with "the filename, directory name, or volume label syntax is incorrect" — silently, with
  no log file ever created. Fixed by building the `/d /s /c "..."` command line as one raw string
  assigned to `ProcessStartInfo.Arguments` instead, which .NET passes through unescaped. Confirmed
  by minimal repro (a bare `echo hello > "path"` failed identically) before and after the fix.
  Worth flagging because `CliWrapProcessRunner.RunShellAsync` (mf-watch, worker-controller) uses
  `ArgumentList` for its own `cmd /d /s /c` invocations too — it likely works for those callers
  only because CliWrap's own argument formatter differs from `ProcessStartInfo.ArgumentList`'s, or
  because no caller's command line has happened to combine embedded quotes with spaces in a way
  that triggers it. Not touched as part of this fase (out of scope; mf-watch's `RunShellAsync` is
  a different, already-shipped code path), but a real one to be aware of if `notify_command`
  (mf-watch) or a build/test `command:` (worker-controller) with embedded quotes ever misbehaves
  the same way.
- **Multi-service partial failure on `start`/`restart`**: not addressed by the design. Each
  service is started independently and best-effort — one failing does not stop the others from
  being attempted — with the overall exit code non-zero if any failed. Symmetric with `status`'s
  already-specified "exit 0 only if everything asked about is running."
- **`run.command` spawn failure in the worker**: the design says a stop/start failure is handled
  by exit code; it doesn't address the executable not existing at all (e.g. `mf-run` not on PATH).
  Treated identically to a non-zero exit — wrapped in a try/catch that converts any exception into
  a synthetic failed `ProcessResult`, so the refusal/warning posture is the same either way.
- **Reverting `status: running` back to `ready` on a stop failure**: by the time planning succeeds
  (the earliest point a stop failure can be detected — the design is explicit that stop must not
  fire during planning), `TaskRunner` has already committed `status: running` before the plan loop
  even starts. Honoring the design's "leave the command ready" therefore means an explicit second
  bookkeeping commit that reverts status and stages whatever the plan phase produced (evidence
  dir, and the plan file if the agent wrote one) — otherwise the working tree would be left dirty
  and the *next* run would immediately hit the dirty-tree guard, the exact self-inflicted deadlock
  the design's own "Repo hygiene" section warns about for `mf-watch.log`. Confirmed end-to-end:
  `git status --porcelain` is empty immediately after a simulated stop failure.

## Not done / left for later

- No health check or URL polling on start — "the process is alive" is the entire v0.1 contract,
  exactly as scoped; whether the app serves correctly is left to the human who's about to look at
  it.
- No cockpit service card — designed against (this CLI's stable exit-code/output contract), not
  built; explicitly deferred by the design itself.
- The E2E stub fixtures (stub service, stub agent, stub mf-run) are throwaway console apps built
  in a scratch directory during validation, not committed to the repo — same precedent as
  mf-watch's own `.cmd`/PowerShell stub-worker validation script.
- `mf-run`'s own `RunConfig` does not validate that `workdir` (if given) exists on disk at
  config-load time, only that `command` is present as a string — consistent with checking the
  actual file *existence* only at start time (see Deviations), but worth naming explicitly: a
  typo'd `workdir` currently surfaces as a generic process-spawn failure, not a clear "workdir not
  found" message.
